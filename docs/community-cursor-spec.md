# Color of Apple 커뮤니티 구현 지시서

작성일: 2026-10-08. 이 문서는 Cursor AI에 전달하는 구현 요구사항이다.
아래 요구사항을 기준으로 현재 저장소를 확인하고 실제 구현하라. 기존 디자인과 코드 구조를 우선 재사용하라.

## 1. 목적과 범위

사용자가 개인 컬러북에 저장한 팔레트를 무료로 공개하고, 다른 사용자가 앱·웹 프리뷰에 즉시 적용해 본 뒤 자기 컬러북으로 복사할 수 있는 커뮤니티를 구현한다.

일반 게시판이나 게시글 상세 페이지 중심으로 만들지 않는다. 넓은 프리뷰 + 작은 팔레트 카드 목록이 핵심이다. 커뮤니티에서는 색상 토큰을 수정할 수 없다. 개인 컬러북으로 복사한 뒤에는 기존 편집 기능을 사용할 수 있다.

첫 출시에 포함:
- 공개 목록, 최신순, 좋아요 많은순, 내 게시물.
- 주사위 5 모양의 색상 점 카드, 선택 카드 확장, 프리뷰 즉시 적용.
- 무한 스크롤, 게시/수정/비공개/삭제, 좋아요/취소, 신고, 공유 링크.
- 내 컬러북으로 복사, 기존 Free 5개 제한과 Pro 무제한 정책 적용.
- 비로그인 탐색, 로그인 이후 작업 이어가기, 한국어/영어 UI.

첫 출시에서 제외:
- 스타일 태그 필터, 커뮤니티 푸터 링크, 댓글, 조회수, 전문 검색, 추천 알고리즘.
- 새 유료 플랜, UI 라이브러리 확장, 결제 변경. 커뮤니티 자체는 Free/Pro 모두 무료다.

## 2. 현재 코드부터 확인할 것

현재 프로젝트는 Next.js App Router, React, Zustand, Firebase Auth/Firestore를 사용한다. 파일 위치는 변경됐을 수 있으므로 구현 시 실제 파일을 확인한다.

- `src/components/brand/site-header.tsx`: 공통 헤더.
- `src/components/brand/site-footer.tsx`: 공통 푸터. 여기에 커뮤니티 링크를 추가하지 않는다.
- `src/components/landing/hero.tsx`: 메인 화면.
- `src/app/result/page.tsx`: 결과 복원과 공유 링크 로딩.
- `src/components/workbench/workbench.tsx`: 프리뷰, 토큰 패널, 개인 컬러북 저장.
- `src/components/workbench/token-panel.tsx`: 기존 편집 패널.
- `src/components/workbench/project-library-dialog.tsx`: 내 컬러북 목록.
- `src/components/preview/preview-canvas.tsx`, `theme-scope.tsx`: 프리뷰 렌더링.
- `src/lib/firebase/data.ts`: 개인 프로젝트 저장과 Free/Pro 제한.
- `src/lib/firebase/admin.ts`: 서버 Firebase Admin 초기화.
- `src/lib/share/`: 공유 팔레트 인코딩/디코딩.
- `src/lib/preview-draft.ts`: 새로고침 복원.
- `firestore.rules`: 개인 프로젝트 권한과 스키마 검증.

기존 프리뷰, 색 생성 엔진, 공유 코덱을 다시 만들지 않는다. 개인 프로젝트 저장 이력, 결제, 웹훅, 플랜 판정은 유지한다. 사용자 작업 중인 코드와 미커밋 변경을 덮어쓰지 않는다.

## 3. 진입 버튼: 같은 화면의 중복을 없앨 것

### 메인 `/`

메인 헤더에만 `커뮤니티 / Community` 버튼을 계정 버튼 앞에 배치한다. 공통 헤더 전체에 무조건 표시하지 말고, 메인 페이지에서 prop 또는 slot으로 활성화한다.

### 프리뷰 `/result`

헤더에는 커뮤니티 버튼을 추가하지 않는다. 오른쪽 패널 상단에 `컬러토큰 / 커뮤니티` 전환을 넣는다. 이 전환을 선택하면 현재 프리뷰와 앱/웹 선택을 유지하고 패널만 바뀐다.

### 커뮤니티 직접 진입 `/community`

커뮤니티 패널이 기본으로 활성화된 프리뷰 화면을 제공한다. 별도의 헤더 커뮤니티 버튼을 중복 표시하지 않는다. 편집할 개인 프로젝트가 없으므로 `컬러토큰` 탭을 눌러 편집 화면으로 넘어가게 하지 않는다. 개인 저장 후 `내 컬러북에서 열기`로 편집에 진입한다.

### 내 컬러북 프로젝트 메뉴

메뉴 이름은 짧게 `게시 / Publish`로 한다. 이미 게시한 프로젝트는 `게시 관리 / Manage post`로 표시한다. 길게 `커뮤니티에 게시하기`를 버튼명으로 쓰지 않는다.

### 푸터

커뮤니티 링크를 넣지 않는다. 기존 플랜·정책·회사소개·문의 링크를 유지한다.

## 4. 프리뷰 상태와 편집 상태를 분리할 것

`/result`에서 개인 팔레트 편집 중 커뮤니티로 전환해도 원래 편집 내용을 덮어쓰지 않는다.

- 커뮤니티에서 선택한 공개 팔레트는 별도 상태로 관리한다.
- 프리뷰에 전달하는 테마만 선택 공개 팔레트로 교체한다.
- 컬러토큰 탭으로 돌아오면 원래 개인 프로젝트와 저장하지 않은 수정까지 복원한다.
- 기존 `preview-draft`를 커뮤니티 카드 클릭으로 덮어쓰지 않는다.
- 커뮤니티 상태와 개인 프로젝트 draft의 저장 키를 분리한다.
- 앱/웹, 프리뷰 종류 전환은 프리뷰 UI 설정만 변경한다. 공개 팔레트 DB에는 쓰지 않는다.
- 직접 방문에서는 현재 기본 프리뷰를 먼저 보여주고 선택을 유도한다. 목록 첫 카드를 자동 선택해도 되지만 추가 DB 조회를 발생시키지 않는다.
- 공유 주소는 `/community?post={postId}`로 한다. 해당 글을 초기 목록에서 찾을 수 없을 때만 단건 조회한다.
- 삭제되거나 비공개인 공유 주소에는 안내를 보여주고 일반 목록으로 이동할 수 있게 한다.
- 새로고침 시 선택 글 ID와 앱/웹 설정을 복원한다. 세션 내 캐시가 있으면 재사용하며, 캐시가 없으면 단건 조회가 필요할 수 있음을 비용 문서에 명시한다.

커뮤니티 모드에서는 토큰 편집, 컬러 피커, 랜덤 생성, 개인 프로젝트 덮어쓰기 동작을 노출하지 않는다. API에도 공개 글의 색을 제3자가 변경할 수 있는 경로를 만들지 않는다. 프리뷰 주변에 `커뮤니티 미리보기 · 읽기 전용` 상태를 표시한다.

## 5. 커뮤니티 패널 및 팔레트 카드

### 패널 상단

`최신순 / Latest`, `좋아요 많은순 / Most liked`, `내 게시물 / My posts`만 제공한다. 스타일 태그 필터를 만들지 않는다. 내 게시물을 선택한 비로그인 사용자는 로그인 안내를 받는다.

### 기본 카드

카드를 작고 균일한 그리드로 만든다. 패널 너비에 따라 2열 또는 3열을 사용하고, 매우 좁으면 1열을 허용한다. 좁은 기존 패널을 무리하게 3열로 만들지 않는다. 프리뷰 공간이 줄지 않도록 패널 너비는 기존 레이아웃을 기준으로 조정한다.

색상 막대나 큰 UI 샘플 대신 주사위 숫자 5의 점 배치를 사용한다.

```text
●       ●
    ●
●       ●
```

대표 색상 5개는 같은 의미의 토큰을 일관되게 사용한다. 예: Primary, Secondary, Accent, Surface, Text. 각 토큰은 실제 프로젝트의 토큰 경로로 매핑하고, 값이 없을 때는 명시적인 호환 처리를 한다. 점에 임의 색을 추가하거나 현재 엔진으로 다시 생성하지 않는다.

흰색 점이 사라지지 않도록 얇은 중립 테두리를 사용한다. 점마다 접근성 설명/툴팁으로 역할과 HEX를 제공한다. 카드 자체에는 제목 한 줄, 공개 닉네임, 좋아요 개수를 간결하게 표시한다.

카드 선택과 좋아요를 서로 다른 버튼으로 만든다. 버튼 안에 버튼을 중첩하지 않는다. 좋아요 클릭으로 프리뷰 선택이나 카드 펼침이 발생하지 않게 한다.

### 선택한 카드 확장

- 한 번에 하나의 카드만 펼친다.
- 펼친 카드는 현재 그리드 전체 열 너비를 사용한다.
- 팔레트의 기존 순서는 유지한다. 선택 카드를 목록 최상단으로 끌어올리지 않는다.
- 선택 카드가 속한 행을 기준으로 확장 영역을 배치하고, 다른 카드들은 위아래 그리드에서 계속 표시한다. 같은 행의 남은 카드도 누락하거나 중복하지 않는다.
- 펼친 카드에는 큰 5점 팔레트, 제목, 설명, 닉네임, 게시일, 선택 태그, 좋아요, 저장, 공유, 더보기 메뉴를 표시한다.
- 태그는 게시 시 선택 메타데이터로 유지하되 상단 필터로 사용하지 않는다.
- 다시 누르거나 닫기 버튼을 누르면 상세 영역만 접는다. 프리뷰에 적용된 팔레트는 유지한다.
- 다른 카드를 선택하면 기존 상세 영역은 접고 새 카드가 펼쳐진다.
- 확장/접힘 시 스크롤 위치가 크게 튀지 않도록 선택 행을 기준으로 보정한다. 프리뷰는 페이지 이동 없이 즉시 반영한다.
- 레이아웃 애니메이션은 짧게 하고 reduced-motion 설정을 존중한다.

### 모바일

프리뷰와 펼칠 수 있는 커뮤니티 하단 패널을 제공한다. 카드 목록 자체에 스크롤 컨테이너를 두고, 펼친 상세를 읽거나 프리뷰를 넓게 볼 수 있게 한다. 기존 헤더/푸터에 카드 패널이 가려지지 않게 한다.

## 6. 무한 스크롤

`더 보기`를 기본 로딩 버튼으로 사용하지 않는다. 패널 스크롤 끝에서 다음 묶음을 자동으로 가져온다.

- 첫 조회는 12개. 후속 조회도 12개씩.
- 패널 내부 스크롤을 root로 하는 IntersectionObserver를 사용한다.
- sentinel이 마지막 카드 근처 약 100~200px 범위에 도달했을 때만 로딩한다.
- 요청 중에는 동일 커서 요청을 재실행하지 않는다.
- 끝에 도달하면 더 이상 조회하지 않는다.
- 12개 미만을 받으면 끝으로 판단한다. 정확히 12개로 끝나는 경우 다음 빈 조회 한 번이 발생할 수 있다. 이를 비용 0으로 설명하지 않는다.
- 아직 사용자가 스크롤하지 않았는데 초기 화면을 채우려고 계속 다음 페이지를 자동 조회하는 연쇄 로딩을 막는다.
- 카드 확장으로 sentinel 위치가 바뀌었다고 불필요하게 여러 페이지를 읽지 않는다.
- 정렬 변경 시 목록/커서/요청 상태를 정렬별로 관리한다. 이전 정렬 응답이 새 목록에 섞이지 않게 취소 또는 request key로 무시한다.
- 실패 시 목록을 유지하고 `다시 시도` 버튼을 제공한다. 자동 무한 재시도를 하지 않는다.
- 이미 가져온 문서는 ID로 중복 제거한다. 이전으로 스크롤해도 재조회하지 않는다.
- 긴 목록에서 DOM 비용이 문제가 되면 윈도잉/가상화를 적용한다. 이는 DOM 절감이며 Firestore 읽기 절감과 혼동하지 않는다. 과한 새 라이브러리는 피한다.

같은 36개 문서를 읽는다면 더 보기 3묶음과 무한 스크롤 3묶음의 문서 읽기량은 같다. 차이는 무한 스크롤이 추가 데이터를 자동으로 읽기 쉽다는 점이다. 36개를 보면서 카드를 수십 번 바꿔도 선택/프리뷰 적용 자체는 추가 Firestore 읽기·쓰기 0회다. 좋아요 상태 조회, 직접 링크 단건 조회, 인덱스 비용 등은 별도다.

## 7. 게시와 게시 관리

### 게시 모달

내 컬러북 프로젝트에서 `게시`를 누르면 다음 필드를 보여준다.

- 게시할 팔레트의 5점 미리보기.
- 제목: 필수, 기존 컬러북 제목 기본값, 1~60자.
- 설명: 선택, 최대 500자.
- 태그: 선택, 최대 3개, 태그당 최대 20자. 필터 용도가 아닌 설명용이다.
- 공개 닉네임: 필수, 1~30자. 로그인 이메일을 자동 노출하지 않는다. 사용자가 공개할 이름을 확인한다.
- 공개되는 색과 정보 확인 안내.
- CTA: `게시` 또는 이미 게시된 경우 `업데이트`.

저장하지 않은 편집 상태에서 게시하려면 기존 저장을 먼저 수행하고 그 저장된 상태를 게시한다. 이 경우 CTA는 `저장 후 게시`다. 저장 실패/슬롯 초과 상태에서 게시를 성공 처리하지 않는다.

### 독립된 스냅샷

공개 게시물은 게시 시점의 복사본이다. 개인 컬러북을 수정하거나 삭제해도 공개 글은 자동 변경/삭제하지 않는다. 개인 프로젝트 삭제 확인에는 공개 글은 별도 관리된다는 안내를 넣는다.

같은 개인 프로젝트는 하나의 공개 게시물에 연결한다. 연속 클릭, 네트워크 재시도, 여러 탭에서 동시 게시해도 중복 글이 생기지 않도록 서버 트랜잭션과 프로젝트별 연결 문서를 사용한다.

게시 관리에는 내용 수정, 현재 저장된 팔레트로 업데이트, 비공개 전환, 재공개, 삭제를 제공한다. 일반 수정으로 최초 게시일을 바꿔 최신순 상단으로 계속 올라가게 하지 않는다. 삭제 후 재게시 반복은 로그인 사용자별 게시 요청 제한으로 제어한다.

## 8. 개인 컬러북에 가져오기

흐름: `카드 선택 → 프리뷰 확인 → 내 컬러북에 저장 → 이름 입력 → 내 프로젝트에서 열기`.

- 색상 스냅샷을 복사한 독립 개인 프로젝트를 생성한다. 다른 사용자의 원본 프로젝트와 연결해 실시간 동기화하지 않는다.
- 저장 후 명시적으로 `내 컬러북에서 열기`를 제공한다. 열면 기존 편집 기능을 사용할 수 있다.
- 원본 작성자와 공개 게시물 주소를 provenance/source 메타데이터로 남긴다.
- 공개 글이 나중에 삭제되어도 개인 복사본은 유지된다. 원본 주소가 없어졌다면 적절한 안내를 보여준다.
- 로그인이 필요하면 선택 ID와 저장 의도를 유지해 로그인 후 이어서 진행한다.
- 기존 Free 5개, Pro 무제한을 서버/Firestore 규칙과 일치하게 적용한다. 커뮤니티 복사로 한도를 우회하지 않는다.
- 공간이 찼으면 기존 `컬러북 정리 / 플랜 업그레이드` 흐름을 재사용한다.
- 기존 프로젝트 문서에 provenance 필드를 추가하면 `SavedProject`, 읽기 변환, 저장 경로, `validProject()` 허용 필드, 테스트를 함께 수정한다. 기존 데이터에 이 필드가 없어도 정상 동작해야 한다.
- 저장 재시도/중복 클릭으로 여러 개인 프로젝트를 만들지 않는다. 저장 의도별 idempotency를 기존 저장 구조에 맞게 처리한다.

## 9. Firestore 스키마

필드 이름은 실제 코드 규칙에 맞춰 조정할 수 있지만 다음 의미를 유지한다.

```text
communityPosts/{postId}
  ownerUid
  authorName
  title
  description
  tags[]
  status                   // published | hidden
  publishedAt              // 최초 게시 시각, 수정해도 유지
  updatedAt
  schemaVersion
  engineVersion
  likeCount                // 서버만 변경, 0 이상 정수
  palette
    input
    selectedPaletteId
    tokenSnapshot
    overrides

users/{uid}/communityPublications/{projectId}
  postId
  createdAt

users/{uid}/communityLikes/{postId}
  createdAt

communityReports/{postId_uid}
  postId
  reporterUid
  reason
  createdAt
  status                   // open | resolved
```

공개 문서에 이메일, 개인 프로젝트 ID, 개인 색 수정 이력, 결제 정보를 넣지 않는다. `ownerUid`는 권한 검증용 식별자이며 이메일 대신 사용한다. API는 목록에 필요한 공개 필드만 반환한다. 작성자 닉네임은 공개 문서에 복제해서 카드마다 프로필 조회를 하지 않는다.

카드/상세/프리뷰 데이터는 한 공개 문서에 포함한다. 카드 클릭 시 추가 세부 문서를 읽지 않는다. 이미지 업로드 없이 CSS로 5점 팔레트를 렌더링한다. 토큰 스냅샷은 게시 시 실제 색을 유지하는 데 필요한 범위만 저장하며 개인 작업 이력은 포함하지 않는다.

`engineVersion`이 달라도 실제 스냅샷의 색을 우선한다. 게시된 팔레트를 최신 엔진으로 조용히 재생성하지 않는다. 스키마 버전이 호환되지 않으면 안내하고 안전하게 건너뛴다.

## 10. 서버 API와 권한

현재 Firebase Admin 초기화/인증 토큰 검증 코드를 재사용한다. 다음은 권장 API 책임이다. 경로는 프로젝트 관례에 맞춰 조정할 수 있다.

```text
GET    /api/community/posts?sort=latest|liked&cursor=...
GET    /api/community/posts/{postId}
GET    /api/community/mine?cursor=...
POST   /api/community/posts
PATCH  /api/community/posts/{postId}
DELETE /api/community/posts/{postId}
POST   /api/community/posts/{postId}/like      { liked: true | false }
POST   /api/community/like-status             { postIds: [...] }
POST   /api/community/posts/{postId}/report
```

- 공개 목록은 인증 없이 published만 반환한다.
- 내 게시물은 로그인 uid의 게시물만 반환하며 hidden도 포함한다.
- 게시 API는 로그인 uid가 소유한 실제 개인 프로젝트를 서버에서 읽고 공개 스냅샷을 만든다. 클라이언트가 보낸 ownerUid/작성자 권한을 신뢰하지 않는다.
- 업데이트/비공개/삭제는 소유자 또는 운영자만 가능하다.
- 각 요청의 문자열 길이, 태그 수, 색상 값, 토큰 크기, ID 형식, 커서 형식과 정렬값을 검증한다.
- 커서와 페이지 크기를 클라이언트가 조작해 전체 목록을 한꺼번에 받지 못하게 한다. 페이지 크기는 12로 서버에서 제한한다.
- 인증 응답과 내 게시물은 `private/no-store`로 처리한다. 사용자별 정보를 공개 캐시에 섞지 않는다.
- 서버 SDK는 Firestore rules를 우회한다. API에서 소유권과 데이터 유효성을 반드시 검사한다.
- 새 커뮤니티 컬렉션을 클라이언트에서 직접 읽거나 쓰지 않는 구조라면 rules에서 직접 접근을 차단하고 API만 사용한다. 이 차단만으로 서버 API가 보호되는 것은 아니다.
- 기존 개인 프로젝트/프로필 규칙은 유지하며 provenance 확장만 필요한 만큼 수행한다.
- 게시/좋아요/신고 요청에 사용자별 서버 제한을 둔다. 무한 스크롤의 정상 읽기까지 과도하게 막지 않는다. 인메모리 제한만으로 여러 서버 인스턴스의 제한을 보장했다고 설명하지 않는다.

신고는 로그인 사용자만 가능하고 같은 사용자/글은 하나로 제한한다. 한 건의 신고로 자동 삭제하지 않는다. 운영자가 확인하고 숨김 처리할 수 있는 절차를 README에 남긴다. 사용자 이메일로 신고를 자동 발송하지 않는다.

## 11. 정렬, 커서, 인덱스

### 최신순

`status == published`, `publishedAt DESC`, 문서 ID를 동률 정렬 기준으로 사용한다.

### 좋아요 많은순

`status == published`, `likeCount DESC`, `publishedAt DESC`, 문서 ID를 동률 정렬 기준으로 사용한다.

### 내 게시물

`ownerUid == 로그인 uid`, `publishedAt DESC`, 문서 ID 동률 정렬. 공개 여부 라벨을 표시한다.

실제 쿼리에 필요한 복합 인덱스를 `firestore.indexes.json` 등 저장소 관례에 맞게 추가하고 배포 방법을 문서화한다. 서버 커서에는 모든 정렬 필드와 문서 ID를 포함하고, 삭제된 커서 문서를 다시 읽어야만 다음 페이지를 가져올 수 있는 방식은 피한다. offset은 사용하지 않는다.

좋아요 수는 페이지 탐색 중 변할 수 있어 인기순 목록에서 중복이나 일부 누락이 발생할 수 있다. ID 중복 제거와 명시적 새로고침을 제공하고, 실시간으로 카드가 계속 재배치되지 않게 한다. 완전히 고정된 순위 스냅샷을 제공한다고 주장하지 않는다. 첫 버전에 복잡한 주기적 순위 배치 작업을 도입하지 않는다.

## 12. 좋아요: 첫 출시에 포함하되 탐색 쓰기를 늘리지 말 것

- 좋아요는 로그인 사용자만 가능하다. 누르지 않고 카드만 보는 것은 쓰기 0회다.
- 좋아요 개수는 공개 문서의 `likeCount`를 그대로 표시한다. 매 카드마다 count 집계 쿼리를 실행하지 않는다.
- 좋아요 여부는 로그인한 사용자가 받은 페이지의 ID들을 묶어서 개인 like 문서를 서버에서 조회한다. HTTP 요청은 묶을 수 있어도 Firestore 문서 읽기 비용까지 1회가 되는 것은 아니다.
- 첫 12개에 대해 좋아요 상태를 조회하면 개인 like 문서 조회가 최대 12건 추가될 수 있다. 비용을 투명하게 문서화한다.
- 사용자별 좋아요 상태를 로컬 메모리에 캐시해 같은 글을 다시 볼 때 재조회하지 않는다. 계정 변경/로그아웃 때 해당 캐시를 초기화한다.
- 서버는 toggle 대신 원하는 상태 `liked: true/false`를 받는다. 재시도 때문에 두 번 뒤집히지 않게 한다.
- 트랜잭션에서 공개 게시물과 개인 like 문서를 읽고, 실제 상태가 달라질 때만 like 문서 생성/삭제 + 공개 likeCount 변경을 원자적으로 처리한다.
- 같은 상태를 다시 요청하면 count를 바꾸지 않는다. 음수 count, 사용자 임의 count 수정, hidden/삭제 글의 신규 좋아요를 막는다.
- 일반적인 상태 변경은 문서 읽기 약 2건과 쓰기 또는 삭제 약 2건이 필요하다. 트랜잭션 충돌/재시도 시 읽기가 늘 수 있다.
- 버튼은 요청 중 연타를 막고, UI는 낙관적으로 반영하되 실패하면 롤백한다. 서버 확정 count를 받아 보정한다.
- 좋아요 하나마다 전체 최신/인기 목록 캐시를 무효화하지 않는다. 현재 사용자의 count는 즉시 갱신하고 다른 방문자의 목록 count/순위는 짧은 캐시 주기만큼 지연될 수 있게 한다.
- 글 삭제 시 하위 컬렉션 자동 삭제를 가정하지 않는다. 위처럼 사용자별 like 문서에 남은 참조는 유효한 게시물로 취급하지 않고, 삭제된 글의 좋아요 해제/계정 삭제 정리 정책을 구현·문서화한다. 전체 사용자 like 컬렉션을 매번 스캔하지 않는다.

## 13. 읽기·쓰기 절감과 캐시

공개 목록에 `onSnapshot`을 사용하지 않는다. 단발 커서 조회와 무한 스크롤을 사용한다.

| 행동 | Firestore 처리 |
| --- | --- |
| 첫 목록 | 공개 문서 최대 12개 조회, 공유 캐시 적중 시 DB 조회 생략 가능 |
| 카드 선택/확장/접기 | 받은 스냅샷 재사용, 추가 읽기·쓰기 0 |
| 앱/웹 전환 | 클라이언트 처리, 추가 읽기·쓰기 0 |
| 다음 묶음 | 최대 12개 추가 조회 |
| 이전 카드 재선택 | 세션 캐시, 추가 조회 없음 |
| 로그인 좋아요 상태 | 해당 페이지의 개인 like 문서 조회, 사용자별 캐시 |
| 좋아요/취소 | 실제 상태가 변경될 때만 트랜잭션 쓰기 |
| 게시/업데이트 | 사용자가 확인한 시점에만 쓰기 |
| 내 컬러북 저장 | 기존 한도 확인/저장 로직의 읽기와 쓰기 발생 |
| 직접 링크 | 초기 목록/캐시에 없으면 단건 조회 |
| 조회수 | 수집하지 않음 |

공개 첫 페이지에는 약 30초의 서버 공유 캐시를 적용할 수 있다. 사용자별 좋아요 상태는 캐시된 공개 결과와 분리해 조합한다. 서버 프로세스의 Map만 사용하고 CDN/분산 캐시라고 부르지 않는다. Next.js/Vercel의 실제 프로젝트 구성에 맞는 캐시 기능을 사용하고 cache key에 정렬/커서를 포함한다.

게시/내용 수정/비공개/삭제 시 관련 공개 캐시를 무효화한다. 비공개/삭제는 이미 클라이언트에 내려간 스냅샷까지 회수할 수 없음을 이해하고, 새 요청과 새 복사 저장에서는 최신 공개 상태를 검증한다. 이미 저장한 개인 복사본은 삭제하지 않는다.

종료된 목록을 반복 조회하지 않는다. 전체 게시물 개수와 전체 좋아요 수를 방문마다 집계하지 않는다. UI의 프리뷰를 볼 때마다 사용자 프로필이나 원본 프로젝트를 조회하지 않는다.

원래 코드의 `subscribeProjects`는 개인 목록 전체를 실시간으로 읽는다. 커뮤니티 화면에서 이 구독을 무조건 시작하거나 유지하지 않는다. 개인 컬러북 모달을 열었을 때만 기존 흐름을 사용하고, 공개 목록만 탐색하는 비로그인 사용자에게 개인 데이터 조회를 발생시키지 않는다.

문서 읽기 외에 복합 정렬에 따른 인덱스 엔트리 읽기, 빈 쿼리 최소 비용, 전송량도 비용에 영향을 준다. 읽기량 추정은 문서 조회 기준인지 전체 과금 기준인지 구분한다. 실제 쿼리 구성과 트랜잭션 재시도까지 측정해 보고한다.

## 14. 완료 검증

다음 시나리오를 의미 있는 테스트와 브라우저 검증으로 확인한다.

1. 메인에만 헤더 커뮤니티 진입 버튼이 보이고 프리뷰에는 패널 전환만 보인다. 푸터에는 커뮤니티 링크가 없다.
2. 카드 2열/3열과 5점 색상이 정상 표시되고 선택 카드가 전체 열 너비로 펼쳐진다. 다른 카드가 사라지거나 중복되지 않는다.
3. 선택 즉시 앱/웹 프리뷰에 실제 저장 토큰이 적용된다. 카드 선택을 반복해도 추가 Firestore 조회/쓰기 요청이 없다.
4. 개인 편집 중 커뮤니티를 방문했다 돌아오면 저장하지 않은 편집 내용이 보존된다. 새로고침 복원과 기존 공유 링크도 유지된다.
5. 무한 스크롤은 12개 단위, 중복 요청 없음, 정렬별 응답 분리, 마지막 페이지 종료, 실패 재시도가 동작한다.
6. 최신순/좋아요 많은순/내 게시물이 서버 쿼리 기준으로 동작한다. 최초 12개만 프런트에서 재정렬하고 전체 인기순이라고 표시하지 않는다.
7. 동일 프로젝트의 게시 재시도/동시 요청이 중복 게시물을 만들지 않는다. 업데이트는 최초 게시일을 유지한다.
8. 남의 게시물을 수정/삭제하거나 likeCount를 직접 조작하는 요청이 거부된다. 공개 API에서 hidden 데이터와 개인 필드가 새지 않는다.
9. 좋아요 같은 상태 재시도, 취소, 연타, 동시 사용자 요청에서 count가 잘못 증가하거나 음수가 되지 않는다.
10. 개인 복사는 원본과 독립이고 Free 5개 한도가 적용된다. 원본 작성자와 주소가 저장되며 기존 프로젝트 문서도 정상 로딩된다.
11. 비로그인 탐색 가능, 로그인 후 저장/좋아요 의도 복원, 계정 변경 캐시 초기화가 동작한다.
12. 데스크톱/모바일에서 카드 확장과 스크롤이 안정적이며 키보드로 선택/좋아요/저장을 사용할 수 있다.
13. 비공개/삭제 후 새 공유 링크 조회와 개인 복사 요청은 차단되고 기존 개인 복사본은 유지된다.

작업 후 lint, type check, 관련 테스트를 실행한다. Firestore Emulator가 준비돼 있다면 권한/트랜잭션을 검증하고, 준비되지 않았으면 실제 검증 여부와 제한을 명시한다. 실사용자 데이터로 파괴적인 테스트를 하지 않는다.

README에는 새 컬렉션, 인덱스와 규칙 배포 방법, 운영자 숨김 처리, 읽기/쓰기 예산, 캐시 동작, 미검증 사항을 남긴다. 키와 사용자 개인정보를 로그/문서/Git에 출력하지 않는다. 환경변수와 배포 설정을 바꿔야 한다면 실제 필요한 항목을 구체적으로 보고한다.

## 15. 구현 순서와 결과 보고

1. 현재 구조와 미커밋 변경 확인, 기존 프리뷰를 재사용하는 컴포넌트 경계 결정.
2. 커뮤니티 타입/서버 API/인덱스/권한과 게시 트랜잭션 구현.
3. 읽기 전용 프리뷰 + 패널 + 주사위 카드 + 확장 레이아웃 구현.
4. 목록 정렬/무한 스크롤/캐시 구현.
5. 내 컬러북 게시 관리와 개인 복사 구현.
6. 좋아요/신고/공유/로그인 의도 복원 구현.
7. 비용 및 동작 검증, README 업데이트.

보고할 내용: 실제 구현 기능, 변경 파일, 검증 결과, 아직 필요한 Firebase 설정, 측정한 사용자 행동별 요청 수. 기능이 없는데 목업 성공 화면으로 완료했다고 보고하지 않는다.
